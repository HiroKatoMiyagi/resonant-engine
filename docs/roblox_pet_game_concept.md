# 仮想ペット育成ゲーム 企画概要（Roblox）

- **仮称**: Bondlings — Nest & Raise
- **プラットフォーム**: Roblox（Luau / Roblox Studio）
- **ジャンル**: 巣づくり（環境構築）× 仮想ペット育成 × 放置進行
- **作成日**: 2026-09-05
- **最終更新**: 2026-09-05（rev.3 — 育成層をケア二層モデルに改訂）
- **ステータス**: 企画段階（未着手）

---

## 1. コンセプト

> **あなたが作った環境が、生まれる命を決める。**
> **あなたの育て方が、その子の未来を決める。**

本作は2つの決定軸を持つ。

| 軸 | 決定するもの | プレイヤーの行為 |
|---|---|---|
| **環境軸** | 何が生まれるか（種） | 巣を建てる |
| **育成軸** | どう育つか（進化先） | 世話をする |

既存のRoblox上のペット系タイトル（Adopt Me!、Pet Simulator 系）では、ペットは
**抽選で決まる静的な戦利品**である。レアリティはRNGが決め、プレイヤーの行動は結果に影響しない。

本作はペットの**種と最終形態の双方をプレイヤーの行動の関数**とする。
2軸が掛け合わさることで、組み合わせは線ではなく面になる。

| 効果 | 内容 |
|---|---|
| 唯一性 | 種と進化の二重分岐により「自分だけの一匹」が構造的に生まれる |
| 見せびらかし価値 | ペットと**巣**の二つの自慢対象。建築スクショはRoblox最強の拡散燃料 |
| トレード価値 | 希少性がRNGではなく**環境構築と手間**に由来するため価値が安定する |
| 継続動機 | 理想の環境も理想の進化も、一日では到達できない |
| 拡散性 | 「同じ卵から違う結果」「この巣で何が孵る？」の双方がSNSで機能する |
| 攻略文化 | 環境と出現種の対応関係がコミュニティの研究テーマになり、Wiki・動画が自然発生する |

### テーマの一貫性

2つの機構は「**プレイヤーの選択が生命を形作る**」という単一のテーマに収束する。
機能追加による焦点の分散ではなく、テーマの強化として設計する。

この年齢層において建築・装飾は最も定着率の高い遊びの一つである。

## 3. コアループ（全体像）

```
ペットが素材を採集（放置中も進行）
   ↓
巣を建てる → 環境属性が変化
   ↓
属性に応じた卵が出現
   ↓
孵化：環境が「種」を決める
   ↓
育成：環境がケアのベースラインを供給し（受動）
      プレイヤーの世話がそれを押し上げる（能動）
   ↓
両者の組み合わせが「進化」を決める
   ↓
育ったペットがより良い素材を採る
   ↓
より特殊な環境が作れる ──→ 最初に戻る
```

**閉じた自己強化ループ**である。建築層とペット層が相互に資源を供給し合うため、
どちらか一方だけを遊ぶことができない構造になっている。

巣は孵化のためのゲートではなく、**孵化後も育成に効き続ける生息環境**である（§5.0）。
これによりプレイヤーの建築投資が一度きりで消費されず、恒久的に意味を持ち続ける。

### 時間軸での3層

| 層 | 周期 | 行動 |
|---|---|---|
| Micro | 30秒〜2分 | 世話アクション、ブロック設置、即時フィードバック |
| Meso | 1日 | 孵化、進化判定、デイリー任務、放置収益の回収 |
| Macro | 1週間〜 | 環境の作り込み、レア種の発見、進化ツリー踏破、トレード、図鑑完成 |

## 4. 巣づくり層（環境構築）

### 4.1 設計課題

建築の自由度と判定の一貫性は、素朴に実装すると両立しない。

| 素朴な実装 | 失敗の形 |
|---|---|
| ブロック配置を厳密に読む | 48時間でWikiに正解が載り、全員が同一の「最適な巣」を建てる。自由度が死ぬ |
| 曖昧に読む | 何を建てても結果が変わらないと感じられ、建築が無意味になる |

### 4.2 解法：環境属性ベクトル

**ブロックそのものを読まず、配置素材から算出される属性値の組み合わせを読む。**

| 属性 | 上げる素材の例 |
|---|---|
| **Heat**（熱） | 溶岩石、炎の結晶、温泉 |
| **Humidity**（湿度） | 水場、苔、霧 |
| **Light**（光） | 発光体、開けた天井 |
| **Nature**（自然） | 草木、花、土 |
| **Mineral**（鉱物） | 岩、鉱石、金属 |
| **Space**（広さ） | 空間の体積、配置密度 |

```
出現卵プール = f(Heat, Humidity, Light, Nature, Mineral, Space)
```

**この方式が機能する理由**

- 建築中に属性メーターがリアルタイムで変動する → 因果が可視化され、ランダムに感じない
- 同一の属性値に到達する建て方が無数に存在する → Wikiが「高Heat × 低Humidity」と示しても、見た目の自由は残る
- マイクラのバイオーム生成（温度・湿度ノイズ）およびポケモンの孵化が採用している実証済みのパターン

攻略情報の存在と、自分だけの巣であることが両立する。

### 4.3 スコープ制約（最重要）

本層は放置すると開発規模を3倍にする。建築・育成・放置・トレードは本来3本のゲームであり、
企画倒れの最頻出パターンがこれである。**以下を明示的に切る。**

| 切るもの | 理由 |
|---|---|
| 自由変形のボクセル地形 | データ量・パート数・複製コストが許容範囲を超える |
| 採掘・サバイバル・戦闘 | 別ジャンル。ペット育成の焦点が消失する |
| 無限ワールド | DataStore の容量制限（1キー約4MB）に収まらない |

**採用する形式：固定サイズの「巣プロット」へのスナップ配置**

- グリッドサイズ：24×24（Phase 1）／拡張可能
- 配置物：地形タイル＋装飾プロップ（すべて事前定義アセット）
- Bloxburg / Islands と同方式。データ量が上限内に収まり、パート数も制御可能
- 「建てている」という感触は完全に成立する
- **プロット拡張はそのまま強力な Game Pass になる**

## 5. 育成層（ケアと進化）

### 5.0 巣は「孵化装置」ではなく「生息環境」である

**孵化後も同じプロットが育成に効き続ける。** これは設計上の重要な決定である。

巣を孵化のためだけのゲートにすると、孵化した瞬間にプレイヤーが作り込んだ
ビルドの役目が終わり、以後はただの飾りになる。建築要素を持つゲームとして
これは致命的な損失である。

同一プロットを時間軸で二役に使う：

| 時期 | 巣の役割 |
|---|---|
| 孵化前 | 環境属性が**出現する種**を決める（§4） |
| 孵化後 | 環境が**ケアのベースライン**を継続供給する（§5.2） |

これにより「孵化用の環境」と「育成用の環境」という2つのシステムを持たずに済む。
概念上はシステムが増えるのではなく、**統合されて減っている**。

### 5.1 ケアの二層モデル

育成は「メニュー選択による能動ケア」と「環境による受動ケア」の
**二層で構成する**。両者は対立する選択肢ではなく、役割が異なる。

| 層 | 仕組み | 性質 | 提供するもの |
|---|---|---|---|
| **能動ケア** | プレイヤーの直接行動 | 離散・即時・意図的 | 精度、愛着、毎日戻る理由 |
| **環境ケア** | 生息環境が継続供給 | 連続・自動・設計的 | 基礎値の底上げ、放置耐性、作り込みの報酬 |

### 5.2 結合方式：ベースライン と ピーク

環境ケアを単純な「ボーナス加算」にしてはならない。それでは環境がただの数値バフとなり、
建築の面白さが失われる。**役割そのものを分離する。**

```
環境ケア = 各ケア軸の「ベースライン（均衡点）」を決定する
能動ケア = ベースラインから一時的に押し上げる

各軸は時間経過でベースラインへ向かってドリフトする
進化判定は「実測値の累積」で行う
```

この方式が生む4つの性質：

| # | 性質 | 効果 |
|---|---|---|
| 1 | 良い環境なら放置しても崩壊しない | 低頻度・無課金プレイヤーが救われる。健全性原則と整合 |
| 2 | 最高到達点には能動ケアが必要 | ベースラインは均衡点であって天井ではない。ヘビー層に上が残る |
| 3 | 環境で「育ちやすい方向」を設計できる | 静かで暗い巣は Rest が高止まりし、自然に Titan 系へ寄る。**狙った系統のための環境設計**という遊びが生まれる |
| 4 | 環境に逆らう育て方ができる | §5.3 参照 |

### 5.3 逆張り進化（Contradiction Evolution）

> **環境の傾向と能動ケアが逆方向のとき、特殊な進化が発生する。**

高Rest環境で毎日 Play 漬けにする、溶岩環境で氷属性を育てる、静寂の巣で
暴れん坊を育てる — **矛盾が希少性を生む**。

- コミュニティが探索するタイプの発見要素であり、攻略動画・Wikiが量産される
- 実装コストはほぼゼロ（進化判定式に条件を1つ追加するのみ）
- 「環境で決まる」を裏切れる余地を残すことで、環境が運命ではなく**素材**になる

### 5.4 ケアパラメータ（4軸）

| 軸 | 能動ケア | 環境ケア（ベースラインを上げる設置物） | 系統への影響 |
|---|---|---|---|
| **Nourish**（栄養） | 餌を手渡す・特殊フード | 餌箱、実のなる木 | 体格・耐久 |
| **Play**（遊び） | 一緒に遊ぶ・散歩 | 遊具、広い空間 | 俊敏・活発さ |
| **Rest**（休息） | 寝かしつける | 寝床、遮光、静音な配置 | 落ち着き・特殊能力 |
| **Clean**（清潔） | 洗う・整える | 泉、流水 | 見た目の品位・希少進化の前提 |

### 5.5 設置物が3つの役割を兼ねる（統合の要）

**建築オブジェクトを、環境属性・環境ケア・能動ケアの3つに同時に作用させる。**
これが二層モデルを「2つのメニュー」ではなく「一つの世界」として成立させる鍵である。

| 設置物 | 環境属性（§4） | 環境ケア（受動） | 能動ケア（直接操作） |
|---|---|---|---|
| 泉 | Humidity ↑ | Clean ベースライン ↑ | 触れて洗ってあげる |
| 餌箱 | Nature ↑ | Nourish ベースライン ↑ | 特別な餌を手渡す |
| 遊具 | Space ↑ | Play ベースライン ↑ | 一緒に遊ぶ |
| 寝床 | Light ↓ | Rest ベースライン ↑ | 寝かしつける |
| 発光鉱石 | Light ↑ / Mineral ↑ | — | — |

オブジェクトを1つ設置するだけで最大3つの意味が発生するため、
**システム数を増やさずに深度だけを増やせる**。プレイヤーの体験としても
「メニューを開いて世話する」ではなく「世話ができる家を作る」になる。

### 5.6 能動ケアの操作形式

**3D操作を主、メニューを補助とする。**

Roblox は3Dソーシャルプラットフォームであり、身体的インタラクションが
ネイティブな表現である。餌を持って運ぶ、ボールを投げる、抱き上げる —
この形式の方が愛着が生まれ、かつ**動画クリップとして強い**（§10 バイラル設計に直結）。

ただし**ケアを労働にしてはならない。** 想定プレイスタイルは1日2回×5〜10分である。

| 原則 | 実装 |
|---|---|
| 3D操作は「気持ちいいが短い」 | 1アクション10〜20秒。連打や長時間拘束を課さない |
| 一括ケアのメニュー経路を常設 | 時間がない日でも完結できる。**無課金で利用可能** |
| Auto-Care（Game Pass）の位置づけ | 補助経路の自動化。面倒の回避ではなく選択肢の追加として設計する |

### 5.7 進化分岐の例

4軸の**累積実測値のバランス**で進化先が決まる。種が同じでも進化先は分岐する。

| 育成傾向 | 進化系統 | 特徴 |
|---|---|---|
| Play 偏重 × Rest 低 | Swift 系 | 高速・小型・採集速度型 |
| Nourish 高 × Rest 高 | Titan 系 | 大型・低速・採集総量型 |
| Clean 高 × 全軸均衡 | Harmony 系 | 稀少。全能力中庸だが専用外見 |
| 極端な偏り（1軸のみ突出） | Wild 系 | 個性的な外見。ネタ枠として拡散しやすい |
| **環境傾向と能動ケアが逆行** | **Contrary 系** | **最稀少。§5.3 の逆張り進化** |
| 全軸低位のまま放置 | Dozing 状態 | **死亡しない**。眠るだけで、世話再開で復帰可能 |

> **設計判断**: ペットは死亡させない。
> 子ども向けプラットフォームにおける喪失体験への配慮であり、
> 同時に既存の携帯型育成玩具の象徴的機構との距離を取る意図もある（§11参照）。
> 環境ケアのベースライン機構により、放置しても Dozing 止まりで回復可能な設計とする。

### 5.8 区画（ゾーン）

種が増えると、それぞれが求める環境が異なってくる。氷系と炎系は同一区画で
最適化できない。結果として：

> 「プロットを区切って種ごとに最適な環境を作りたい」→「場所が足りない」

という欲求が**プレイヤー自身の野心として自然発生する**。
Plot Expansion（§7.1）はこの欲求に応える形になり、煽って売る必要がない。
§7.2 の健全性原則に沿った、最も理想的な購買動機である。

## 6. 放置進行層

ペットはオフライン中も素材とBonds（ゲーム内通貨）を生成する。
**ケア状態が良好なほど、また環境が種に適しているほど効率が上がる。**

```
放置収益 = ペット基礎値
         × ケア状態係数(0.5〜2.0)
         × 環境適合係数(0.5〜1.5)   ← 巣がその種に合っているか
         × 進化段階倍率
         × 育成枠数
```

環境適合係数により、「その子に合った巣を作る」という第二の建築動機が生まれる。
コレクションが増えるほど、種ごとに最適化した区画を作りたくなる構造。

## 7. 収益設計

巣づくり層の追加により、課金面が**健全な方向に約2倍**になる。
建築系の課金は構造的に Pay-to-Win になり得ない（装飾と空間しか売らない）ため、
収益面が拡大しつつ倫理リスクは増えない。

- 限定環境でのみ孵化する季節種
- シーズンパス（無料トラック＋有料トラックの二層構成）

### 7.2 健全性の設計原則

収益性と健全性はトレードオフではない。長期運営されている
Roblox タイトルはいずれも非略奪的な設計を採用している。

| 原則 | 具体的な実装 |
|---|---|
| **Pay-to-Win を作らない** | 課金対象は「時短」「見た目」「空間」「枠」に限定。能力を直接売らない |
| **無課金で全到達可能** | すべての種・進化系統は無課金で到達できる。差は所要時間のみ |
| **確率の明示** | 卵のレアリティ確率をゲーム内で常時開示 |
| **射幸性の抑制** | 連続ガチャ演出・敗北演出を用いない。天井（一定回数で確定）を設置 |
| **選択肢を奪わない** | 課金しないことによるペナルティを設けない。進行が止まる設計にしない |
| **年齢への配慮** | 支出を煽る通知を送らない。カウントダウン型の購入圧を用いない |

> この原則は倫理面の要請であると同時に、
> プラットフォームのポリシー変更・各国の課金規制強化に対する
> 事業リスクヘッジでもある。

## 8. リテンション設計

- **デイリーケア枠**: 1日2回（朝／夜）。過度な拘束を避け、逃した場合のペナルティも設けない
- **7日連続ログイン**: 確定レア卵。ただし途切れてもリセットせず累積式にする
- **図鑑（Bondex）**: 種 × 進化系統のマトリクス。長期目標として機能
- **環境レシピの発見**: 未発見の属性組み合わせを見つけると図鑑に記録される。探索的な長期目標
- **週次イベント**: 限定バイオーム素材・限定種。運営継続の中核
- **トレード経済**: プレイヤー間取引が自律的にリテンションを生む（Adopt Me! の本質）

## 11. 法務・権利チェックリスト

### 前提となる法的理解

ゲームの**ルールやシステムはアイデアであり著作権で保護されない**
（釣りゲータウン2事件・知財高裁 2012年、2013年確定）。
「卵から孵る」「世話をする」「環境で出現種が変わる」「ブロックを置いて建てる」
といった仕組み自体に法的問題はない。保護されるのは具体的な表現である。

ブロック建築については Roblox 上にも Islands、Lumber Tycoon 等の先行例が多数あり、
プラットフォーム上で確立されたジャンルである。

### 遵守事項

| 区分 | ルール |
|---|---|
| **命名** | 既存の携帯型育成玩具ブランドの名称・その語尾を模した命名を使用しない。またブロック建築ゲームの著名タイトル名および "-craft" 系の語を使用しない |
| **キャラクター** | 完全オリジナルデザイン。既存キャラの参照素材を制作フローに入れない |
| **ペット造形** | 著名ブロック建築ゲームの固有クリーチャー（緑の柱状体、長身の黒い人型 等）を想起させる造形を避ける |
| **人型造形** | 角ばった直方体の人型キャラクターを模さない |
| **テクスチャ** | **16×16ピクセルの土・草ブロック質感を再現しない**。当該テクスチャは象徴的であり著作権保護の対象 |
| **ビジュアル全般** | 卵型3ボタン筐体UI・モノクロドット絵の再現を行わない。独自のアートスタイルを確立する |
| **音源** | 自作またはライセンス取得済みのもののみ使用 |
| **宣伝文言** | 既存ブランド名を用いた比較訴求を行わない |

### 宣伝文句の置換表

| ✕ 使用禁止 | ○ 使用する |
|---|---|
| （育成玩具ブランド名）風 | virtual pet / 仮想ペット育成 |
| （ブロック建築タイトル名）風 | sandbox building / nest building |
| （ブランド名）ライク | egg hatching / pet raising |
| （ブランド名）の3D版 | environment-driven hatching / care-based evolution |

> **重要**: 本ドキュメント内および開発チーム内での既存製品への言及は
> 設計上の参照に留め、**公開されるいかなるテキストにも残さないこと**。
> 本書が外部に共有される可能性を考慮し、本文中では固有名を用いていない。

### 立方体グリッドの扱い

立方体ブロックを格子状に配置するという**仕組み**は保護されない。
問題になるのは**見た目を借りること**である。この線引きを守る限り、
ブロック建築の採用自体にリスクはない。アートスタイルは意図的に
独自方向（例：柔らかい有機的フォルム、非ピクセルのマテリアル表現）へ振る。

### プラットフォームリスク

Roblox は 2024年3月に **Rights Manager** を導入しており、権利者による削除申立てが可能。
DMCA 申立てを受けた場合：

- ゲームが即時削除される（異議申立ては可能だが復旧に時間を要する）
- 繰り返すとアカウント自体が終了（repeat infringer policy）
- 蓄積した収益基盤とプレイヤーがすべて失われる

**訴訟リスクよりもプラットフォーム側の一存で事業が消えるリスクの方が実務上は深刻。**

### 推奨アクション

1. ゲーム名とキーアートが確定した段階で、知財専門弁護士による事前クリアランスを受ける
2. 自ゲーム名の商標出願を検討する（他者による先取りの回避）
3. 参照すべきモデルは既存の他社製品ではなく、
   **Roblox 上で成功している Adopt Me! / Pet Simulator / Bloxburg の設計思想**とする

## 12. 技術構成

| 領域 | 方針 |
|---|---|
| 言語 / 環境 | Luau / Roblox Studio |
| データ永続化 | ProfileService 相当（セッションロック必須。データ消失は致命的） |
| **巣データ** | 事前定義アセットIDとグリッド座標の配列として保存。ジオメトリそのものは保存しない。24×24 で 1キー4MB 制限内に十分収まる |
| **属性算出** | サーバー側でバッチ計算。ブロック設置ごとの逐次再計算は行わず、確定時にまとめて評価 |
| **ケアのベースライン／ドリフト** | 環境属性から算出したベースラインをプロット単位でキャッシュし、巣の変更時のみ再計算。ケア値のドリフトは実時間の差分から遅延評価する（毎フレーム更新やタイマー常駐は行わない） |
| **オフライン期間の扱い** | ログイン時に前回時刻との差分からドリフト後の値を一括算出。オフライン中の常駐処理は不要 |
| 権威モデル | **完全サーバー権威**。ケア処理・孵化抽選・進化判定・属性算出・通貨増減はすべてサーバー側 |
| 乱数 | 孵化抽選の乱数生成はサーバーのみ。クライアントに抽選結果を先渡ししない |
| クロスサーバー | MemoryStoreService（トレードキュー・グローバルイベント） |
| 負荷対策 | StreamingEnabled、巣プロットのパート数上限、ペット描画のLOD、放置演算はバッチ処理 |
| 不正対策 | クライアント入力は全て検証。配置座標の妥当性チェック。異常値検出ログ。リモートイベントのレート制限 |

## 14. リスクと対応

| リスク | 深刻度 | 対応 |
|---|---|---|
| **スコープ肥大による企画倒れ** | **最高** | §4.3 の「切るもの」を厳守。建築は固定プロットのスナップ配置に限定し、ボクセル・採掘・戦闘を作らない |
| 建築層と育成層の焦点分散 | 高 | 「プレイヤーの選択が生命を形作る」という単一テーマに両者を接続する。無関係な機能は追加しない |
| 属性→種の対応が単調に感じられる | 高 | Phase 0 で最優先検証。組み合わせ数と発見の density を調整する |
| **ケアが労働化する** | 高 | 1アクション10〜20秒の上限を守る。一括メニューを無課金で常設し、逃した日のペナルティを設けない（§5.6） |
| 環境ケアが強すぎて能動ケアが無意味になる | 中 | 環境はベースライン（均衡点）のみを決め、天井は決めない。上位進化には能動ケアの累積を必須とする（§5.2） |
| ジャンル飽和による埋没 | 高 | 「環境で種が決まる × ケアで進化が決まる」の二重分岐に集中する。機能を増やして薄めない |
| 初動での露出獲得失敗 | 高 | ローンチ前にクリエイター配布・事前コミュニティ形成を行う |
| 巣データによるDataStore圧迫 | 中 | アセットID＋座標配列形式を厳守。プロットサイズに上限を設ける |
| 建築のパフォーマンス負荷 | 中 | プロットあたりのパート数上限、StreamingEnabled、訪問時のLOD |
| 運営継続コスト | 中 | 週次更新の自動化基盤（バイオーム素材のデータ駆動化）を Phase 1 で作る |
| 自分がクローンされる側になる | 中 | メカニクスは模倣される前提。運営速度とコミュニティで差をつける |
| データ消失事故 | 高 | セッションロック必須。バックアップとロールバック手順を Phase 1 で確立 |
| 収益の超上位集中 | — | 中央値の収益はほぼゼロという前提で事業計画を立てる。撤退基準を事前に決める |
